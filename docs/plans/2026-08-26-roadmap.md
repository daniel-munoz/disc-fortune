# disc-fortune roadmap (post-v2.0.0)

**Date:** 2026-08-26
**Status:** Approved ordering; individual tasks still need their own designs where noted.
**Basis:** 7-agent weighted vote over 12 candidate improvements. See the "Vote" section
at the end for how this ordering was derived and where the vote should *not* be trusted.

Each task below is written to be handed to a fresh session. A task states its problem,
approach, files, acceptance criteria, dependencies, and whether it needs a design pass
before code.

---

## Phase 1 — v2.1.0 "Durability" ✅ SHIPPED (2026-08-28)

All three tasks landed. In-session decisions, recorded here because later phases
inherit them:

- **T2 backoff constants:** 5 attempts, 1s doubling to a 16s step, 25% jitter,
  60s total-wait cap, `Retry-After` honored when larger.
- **T3 global-flag shape:** global flags are registered inside `newFlagSet`, so
  every command gets them and none can ship without them. Their help text is
  appended to every usage block centrally in `init()`, with a test that fails if
  a command lacks it. **T6 and T7 should follow this pattern.**
- **T3 XDG migration:** notice-only by default, never an automatic move, plus a
  new `migrate` command. The legacy directory keeps winning whenever it holds
  data the XDG path does not.
- **New:** `command.needsConfig` marks which commands require a resolvable config
  directory. New commands that read or write data files must set it.


Closes every defect that was verified against the actual code. No new user-facing
capability, no design debate, no one-way doors. This phase exists because four
independent reviewers made T1 their top pick and none of the three tasks here drew a
serious objection from anyone.

### T1 — Atomic writes

**Problem.** `saveCollection` (`collection.go:70`), `saveHistory` (`history.go:39`) and
`saveFavorites` (`favorites.go:44`) each call `os.WriteFile` directly over the live path.
There is no temp-file-then-rename anywhere. `history.json` is rewritten on *every pick*,
which makes it the highest-frequency write in the tool. A truncated `history.json` does
not merely lose history: `loadHistory` returns a parse error, and `runPick`,
`runHistory`, `favoriteLastPick` and `unfavoriteLastPick` all call it, so the default
command stays broken until a human finds and deletes the file by hand.

**Approach.** One helper, used by all three savers:

```go
func writeFileAtomic(path string, data []byte, perm os.FileMode) error
```

Write to a temp file in the *same directory* as the target (rename is only atomic within
a filesystem), `Sync()` before close, then `os.Rename` over the target. Clean up the temp
file on any error path.

**Files.** New `atomic.go` (or fold into `collection.go`); call sites in `collection.go`,
`history.go`, `favorites.go`.

**Acceptance.**
- All three save paths go through the helper; no bare `os.WriteFile` to a live data path remains.
- A marshal or write failure leaves the pre-existing file byte-identical.
- No `.tmp` residue after a successful write.
- Existing file permissions (0644) are preserved.

**Tests.** Failure injection on the temp write; assert the original file survives. Assert
no stray temp files in the config dir after success. Existing `collection_test.go`,
`history_test.go`, `favorites_test.go` round-trips must keep passing unchanged.

**Depends on.** Nothing. **Do this first** — it is also the safety net for T4's migration.

**Design pass needed.** No. Well-known pattern, single obvious shape.

**Size.** Small.

### T2 — Discogs sync robustness

**Problem.** Four separate gaps in the same code path:

1. `userAgent` (`discogs.go:13`) is the literal `"disc-fortune/1.0"` while `version`
   (`main.go:11`) is `"2.0.0"`. The tool misreports itself to an API whose terms ask for
   accurate identification.
2. `discogsClient.get` has no retry and no backoff. Discogs allows 60 authenticated
   requests/minute; a 429 currently surfaces as a raw response body inside an error and
   aborts the whole sync.
3. `sync` prints nothing until it has finished every page. On a real collection this is a
   silent multi-minute wait with no evidence the process is alive — the newcomer reviewer
   ranked this the single highest-risk moment in the tool.
4. Nothing records *when* the last sync happened, so there is no way to nudge a user
   whose collection is a year stale.

**Approach.** Derive the User-Agent from `version`. Add bounded retry with exponential
backoff on 429/5xx, honoring `Retry-After` when present, with a hard cap on attempts and
total wait. Emit page progress to **stderr** (never stdout — stdout is the data channel)
and only when stderr is a TTY. Record `synced_at` in a new `meta.json` rather than
touching `collection.json`, whose array shape T4 will already be changing.

**Files.** `discogs.go`, `sync.go`, new `meta.go`.

**Acceptance.**
- `User-Agent` header contains the current `version` and cannot drift from it again.
- A 429 followed by a 200 completes the sync successfully.
- Retries are bounded; a persistently failing endpoint still fails, loudly, in finite time.
- Progress output goes to stderr and is absent when stderr is not a TTY.
- `sync` records a timestamp; a later command can read it.

**Tests.** `httptest` server scripted to return 429-then-200, and to return 429 forever.
Assert header contents. Assert stdout stays clean when progress is on.

**Depends on.** Nothing. Shares the fetch loop with T4 — if one person does both, do T2
first and T4 immediately after, in that order.

**Design pass needed.** No, except one small choice to make in-session: backoff constants.

**Size.** Medium.

### T3 — Environment conventions

**Problem.** `configDir()` (`collection.go:34`) hardcodes `~/.config/disc-fortune` and
ignores `XDG_CONFIG_HOME`. `NO_COLOR` is not honored anywhere. Color is decided solely by
`isTTY(os.Stdout)` (`color.go:17`), so `disc-fortune list | less -R` loses all color with
no way to force it back. Separately, `configDir()` calls `os.Exit(1)` on failure, which
makes it awkward to test.

**Approach.** Honor `XDG_CONFIG_HOME` when set and non-empty, falling back to
`~/.config`. Honor `NO_COLOR` (any non-empty value disables, per no-color.org). Add
`--color=auto|always|never`. Make `configDir()` return an error instead of exiting.

**⚠ Migration hazard.** A user who already has `XDG_CONFIG_HOME` pointed somewhere
non-default will, on upgrade, suddenly appear to have lost their entire collection. Do
not ship the naive version. Required behavior: if the XDG-derived directory does not
exist but the legacy `~/.config/disc-fortune` does, keep using the legacy path and print
a one-time notice telling the user how to migrate. Decide in-session whether to offer an
automatic move.

**Open design question.** Flags are currently registered per-subcommand (`cli.go`), so
there is no global flag slot. Either add `--color` to a shared registration helper
alongside the filter flags, or intercept it before dispatch. Pick one and be consistent —
this decision will be copied by every later global flag.

**Files.** `collection.go`, `color.go`, `cli.go`.

**Acceptance.**
- `XDG_CONFIG_HOME` respected when set; legacy path still found when it is the only one present.
- `NO_COLOR=1 disc-fortune` emits no escape sequences.
- `--color=always` survives a pipe; `--color=never` suppresses on a TTY.
- `configDir()` no longer calls `os.Exit`.

**Depends on.** Nothing, but land after T1 so any path change is writing atomically.

**Design pass needed.** Light — the global-flag question above should be settled before code.

**Size.** Medium.

## Phase 2 — v2.2.0 "Identity" ✅ SHIPPED (2026-08-29)

T4 landed. In-session decisions, recorded here because later phases inherit them:

- **Identity is two mechanisms, not one.** `Album.Identity()` is a map key,
  used *only* where every album is known to carry an ID (sync dedup).
  `sameAlbum(a, b)` is a pairwise comparison, lenient when either side has no
  ID. **T5, T7 and T10 must pick the right one:** `Identity()` for anything
  keyed in a map, `sameAlbum` for "is this the same record as that one".
- **`sameAlbum` is not transitive** — an entry with no ID is a wildcard for its
  name. It is only safe in a **first-match** scan. Two defects on this branch
  came from that: `removeFavorite` was a filter-all loop that deleted every
  pressing of a title, and the ambiguity fix stamped an ID without the metadata
  belonging to it. Any new call site needs the same scrutiny.
- **`Album.Key()` stays `"Artist - Title"`** and is the `--query` search text.
  It is not an identity. The roadmap originally specified changing it; doing so
  would have silently broken every query.
- **Backfill runs after the collection is written**, is idempotent, rewrites a
  file only when something changed, and warns without failing the sync.
- **Known limitation carried forward:** `sync` now rewrites `history.json`, so a
  concurrent `pick` can lose its entry. T5 makes history load-bearing for
  picking, so this is worth closing then.

One task, and the riskiest change on the roadmap. It got its own version so it could be
released, and if necessary reverted, on its own.

### T4 — Store the Discogs release ID

**Problem.** `Album.Key()` (`collection.go:27`) returns `Artist + " - " + Title`, and that
string is simultaneously the sync dedup key, the favorites identity, and the history
identity. `collectAlbums` (`sync.go`) dedups through a `seen` map on that key with no
warning, so two distinct pressings of the same title silently collapse into one entry and
one of them vanishes from your collection. An upstream retitle on Discogs orphans a
favorite. The API returns a stable release ID that the tool currently discards.

**Approach.** Add `ReleaseID int \`json:"release_id,omitempty"\`` to `Album`, populated
from `basic_information.id`. `Key()` prefers the release ID when non-zero and falls back
to the legacy string when it is absent. Sync dedup switches to the ID. On load, backfill
IDs into favorites and history entries by matching their legacy key against the freshly
synced collection.

**Known cost, accepted.** This leaves a permanent dual-identity fallback for
pre-migration data. That was the maintainer reviewer's stated objection and the reason
this did not place higher. Bound it: the fallback applies only to entries with no ID, and
the backfill should retire most of them on the first sync after upgrade.

**User-visible consequence.** After re-syncing, the collection count may *increase*,
because pressings that were previously merged now appear separately. This is the bug
being fixed, but it will look like a change in behavior. It must be called out
prominently in the v2.2.0 release notes.

**Files.** `collection.go`, `discogs.go`, `sync.go`, `favorites.go`, `history.go`.

**Acceptance.**
- Two releases with identical artist and title but different IDs both survive a sync.
- A favorites file written by v2.1.0 still resolves after upgrade, with no data loss.
- Backfill is idempotent — running sync twice does not duplicate or corrupt entries.
- Downgrading to v2.1.0 does not destroy the data (Go's JSON decoding ignores unknown fields).

**Depends on.** **T1 must be merged.** This rewrites all three data files; do not attempt
it while writes are still non-atomic.

**Design pass needed.** **Yes — write a design doc before any code.** Migration semantics,
fallback lifetime, and backfill ordering all need to be settled in writing first.

**Size.** Large. Budget a full session for design and a separate one for implementation.

## Phase 3 — v2.3.0 "Discovery" ✅ SHIPPED (2026-08-31)

T5 landed. In-session decisions, recorded here because later phases inherit them:

- **`--unheard` is a filter; `--draw` is a strategy.** `--unheard` narrows the
  candidate pool before a draw happens at all, the way `--favorites` and the
  other filter flags do. `--draw` decides how a draw is made from whatever
  pool survives filtering. **T7 and T9 both need to know which is which:**
  T7's `--json` schema documents them in different places, and T9's `stats`
  reasons about "the candidate pool" independent of how a pick would be
  drawn from it.
- **Every history identity comparison goes through `lastPlayedIndex`'s
  backwards, first-match `sameAlbum` scan.** `excludeRecent`, `unheardOnly`
  and `staleWeights` all resolve "is this the same record as that history
  entry" through it. It must not be replaced with a map: `sameAlbum` is not
  transitive when an entry has no release ID, and a map key would silently
  assume it was. **T9's "share of the collection ever picked" must use the
  same scan**, not build its own index.
- **An un-ID'd history entry is a name wildcard.** It matches every pressing
  sharing its "Artist - Title", not just the one actually played. That is why
  `excludeRecent` falls back to the whole pool when exclusion would empty it,
  and why `--unheard` stays conservative — a wildcard entry counts every
  same-named pressing as heard, not just the one the data can actually
  attest to. A `sync` backfill retires these entries over time.
- **`withFileLock` must never nest.** Two exclusive locks on the same path
  through two file descriptors deadlock even within one process, so a new
  read-modify-write on `history.json` or `favorites.json` belongs entirely
  inside one `withFileLock` call at the outermost layer, never inside another.
- **New `*.lock` sidecars live in the config directory.** Anything
  enumerating that directory — `migrate` today, whatever comes next — has to
  skip them via `isLockSidecar`, or it will treat runtime scaffolding as user
  data.

### T5 — History-aware picking

**Problem.** `randomAlbum` (`collection.go:78`) is a bare `rand.IntN` over the filtered
slice. `history.json` is written on every pick and *never read back into the decision*.
The tool records what you played and then ignores it completely.

**Scope note.** The original ballot split this into three competing options — anti-repeat,
`--unheard`, and weighted picking — which diluted the theme across three lines and pushed
each of them down the rankings. Treat it here as **one feature with three behaviors**,
which is how the maintainer and leverage reviewers both argued it should have been
presented.

**Approach (to be settled in design).** A single scoring pass over candidates, then a
weighted random draw:
- **Anti-repeat**: exclude the last N picks. Candidate default N = 10, or `min(10, len/3)`
  for small collections.
- **`--unheard`**: hard filter to albums that have never appeared in history.
- **Recency weighting**: bias toward records not played in a long time.

**Constraint, from the maintainer's dissent.** Do **not** silently convert `--favorites`
from a hard filter into a soft bias. Anyone scripting against today's behavior would
break with no warning. Keep `--favorites` exactly as it is; if soft weighting of
favorites is wanted, it gets its own flag.

**Files.** `collection.go`, `main.go` (`runPick`), `cli.go`, likely a new `picker.go`.

**Acceptance.**
- Picking is deterministic under a seeded RNG so it can be tested at all.
- Anti-repeat never returns an empty set — it must degrade gracefully when the collection
  is smaller than N.
- `--unheard` on a fully-heard collection fails loudly with an actionable message, per the
  v2 exit-code rule.
- `--favorites` behavior is byte-identical to v2.2.0.

**Depends on.** T4 — history identity should stabilize *before* the tool starts making
decisions from accumulated history, or the same migration has to happen twice.

**Design pass needed.** **Yes.** Three overlapping behaviors and several plausible shapes.

**Size.** Large.

## Phase 4 — v2.4.0 "Composability" ✅ SHIPPED (2026-09-04)

T6, T7 and T8 all landed. In-session decisions, recorded here because later
phases inherit them:

- **The filter grammar is a ceiling, not a foundation.** Values OR within a
  field, different fields AND together, any `--exclude-` match removes the
  record outright — and that is all. No parentheses, no cross-field boolean
  expressions, no regex. A later task wanting richer selection needs its own
  design, not an extension of this one.
- **Two tables describe the filter surface**, and anything enumerating flags
  must read both: `filterFields` for the six substring-matched filters, and
  `nonSubstringFilterFlags` for `--year`, `--decade` and `--release-id`, which
  parse their values instead. The second table exists because those three had
  their help text hand-copied into two places and it drifted.
- **`--release-id` remains the one identifying filter.** Single-valued, no
  `--exclude-` twin, outside `anyNarrowing()`, and the only filter that excuses
  a missing query on `favorite`/`unfavorite`. Any future identifying flag
  should follow that shape.
- **Empty flag values are dropped at parse time, never at match time.**
  `strings.Contains(anything, "")` is true, so an empty exclusion reaching the
  matcher would exclude the whole collection. Every new call site that counts
  or reads flag values goes through `nonEmpty()`.
- **`--json` changes the format, never the semantics.** Any command that gains
  the flag switches its output only: exit codes, stderr and side effects stay
  identical. This is what lets it be added to a command without a release note.
- **`Album` and `jsonAlbum` are hand-kept in step**, and
  `TestEveryAlbumFieldHasAWireDecision` is the forcing function. The golden
  tests pin the emitted bytes; they do **not** catch a field added to storage.
  That distinction cost a review cycle to discover — the design had claimed
  the golden tests covered both.
- **`newHistoryPayload` deliberately duplicates `formatHistory`'s
  clamp-and-reverse.** The duplication is what guarantees the JSON and text
  views agree about "the last N picks". Both sides carry a comment saying so,
  and a test asserts they agree. Change them together.
- **Flag registration lives in `add*Flags` functions, not inline in the parse
  functions.** Completion enumerates the same `FlagSet` a command parses with,
  so a flag cannot be accepted without also being completable.
- **Syntax-checking a generated shell script is not enough.** fish defaults to
  filename completion, so a script that every shell's syntax checker accepted
  still listed the working directory instead of the subcommands. Generated
  scripts need tests that drive the shell's actual completion engine.

Ordered deliberately: filters stabilize before anything generates completions from them.

### T6 — Richer filters
Multi-value OR (`--genre jazz --genre funk`), negation, separate `--artist` / `--title`,
and `--decade 70s`. Extends the existing `Filter` struct (`filter.go`) and the shared flag
registration in `cli.go`. **This is permanent CLI grammar** — settle the OR and negation
syntax in design before implementing, because it cannot be changed later.

**Already shipped in v2.2.1, and T6 must not contradict it:** `--release-id N`
(exact whole-value match, and the one filter that needs no query, because it
identifies rather than narrows), and `--format` matching a pressing's colour via
`basic_information.formats[].text`. The `filterFlags` split of `anyNarrowing()`
vs `identifies()` is the shape any further "identifying" flag should follow.
`TestFilterFlagsAreDocumented` will fail if a new filter flag is not added to
every usage block.
*Depends on:* nothing hard. *Design pass:* yes, for syntax only. *Size:* medium.

### T7 — `--json` output
Machine-readable `pick`, `list`, and `history`. Define and document the schema explicitly
rather than letting it fall out of the structs, and include `release_id` from day one.
*Depends on:* T4, so the ID is in the schema before anyone scripts against it.
*Design pass:* light — schema only. *Size:* small-medium.

### T8 — Shell completion
Generate bash/zsh/fish from the existing `commands` table (`cli.go:80`), which already
holds name, summary and usage. Optionally complete `--genre` and `--label` values from
the local collection.
*Depends on:* T6 — building flag-value completion before the filter grammar settles is
throwaway work. *Design pass:* no. *Size:* medium.

## Phase 5 — v2.5.0 "Insight"

### T9 — `stats` command
Decade histogram, top labels, top genres, share of the collection ever picked. Pure local
derivation from files already on disk; no new write paths, no new failure modes. The
"share ever picked" figure only becomes meaningful once T5 has made history matter.
*Depends on:* nothing hard; better after T5. *Size:* small-medium.

### T10 — `open` command
Open the picked release's Discogs page in a browser.
*Depends on:* **T4** — impossible to do correctly without the release ID.
*Size:* small.

## Ordering rationale, and where to push back

**Why durability first.** T1 took four of seven first-place votes from reviewers who
agreed on nothing else, it is the cheapest item on the list, and it is the prerequisite
that makes T4's migration safe to attempt.

**Why identity before discovery.** History-aware picking accumulates value over time, so
every week it ships *before* the identity fix is another week of history recorded under a
key that will later have to be migrated. Doing T4 first means that migration happens once,
against a smaller file.

**Where this ordering is contestable.** The one reviewer speaking for the person who
actually uses this tool — the record collector — ranked the entire Phase 1 at zero and put
history-aware picking at the top of their ballot. Five of the seven reviewers were
engineering-quality lenses, so a hygiene-first result was close to structurally
guaranteed. If user-visible value matters more than migration efficiency, **swap Phase 2
and Phase 3** and accept that history will need migrating twice. That is a legitimate
call, not a mistake.

**Two caveats that shaped this roadmap more than the raw totals did.**

The picking theme was split across three ballot lines (anti-repeat, `--unheard`, weighted)
while the hygiene items were each presented as bundles. Those three sum to 34 points —
tied for second — but placed 6th, 7th and 11th individually. The vote did not reject
smarter picking; the ballot structure diluted it. Hence T5 being a single task here.

Store-release_id placed 4th on points, yet was named the *hardest omission* by all three
reviewers who left it off. Every ballot engaged with it seriously and none ranked it
first. That is the signature of a broadly-important, nobody's-favorite change, which a
points system of this kind systematically underrates — hence its own phase rather than a
back-of-the-roadmap slot.
